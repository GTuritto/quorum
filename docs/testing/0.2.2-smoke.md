# Validated memory reuse, 0.2.2 candidate

Use a disposable project and a fresh Codex CLI or Claude Code session for
**each** trial. Use synthetic data. The JSON fixture contains inputs and
expected observations, not model results. Structural tests check the written
protocol. Only host traces and answers show what a particular session did.

## Prepare the project

1. From the candidate checkout, run `npm pack --pack-destination /path/to/scratch`.
   Extract that archive in scratch and install with
   `node package/installer/install.mjs --targets codex --project-root /absolute/project`
   or `--targets claude`. Use the resulting project's skill entry, core, memory
   module and helper. Record commit, dirty state and installed SHA-256 hashes.
2. Read [the fixture](../../tests/fixtures/memory-reuse-cases.json) in the
   controller, outside the host project. For each case, write its
   `evidence[case.current]` lines to `current.md`. For an enabled case run
   `node "$helper" on --project-root "$project"`. Send each named fixture record
   as JSON on stdin to `node "$helper" save --project-root "$project"`.
   Keep the generated IDs in the controller. For the changed twin reuse the
   **same project and record** as the compatible run, replace only current.md,
   and start a new host session. Do not give the host the fixture or expected answer.
   Preserve a zero-match run when a host selects a valid but absent phrase.
   To exercise the later stages separately, the named title variant prefixes the
   same decision with `titleVariant` before saving it. This includes the natural
   phrase “Lantern pilot” in the record. Keep prompt and helper identical, run
   both twins on the exact same titled UUID, and report the variant explicitly.
3. Use disposable writable projects because an authorized `select` can create
   and remove the transient project lock. For global scenarios use only an
   isolated synthetic global store. The helper API accepts `{homeDir}` as its
   second argument. An equivalent CLI test binding can preload a test module
   that overrides Node's `os.homedir()` for that helper process alone. Seed
   the synthetic origin, share, preview and admit through the real helper.
   Never change the operator's global settings or account.
4. Start Codex using `codex exec --ephemeral --skip-git-repo-check --json --sandbox workspace-write -C "$project" -`.
   Start Claude Code in the project using `claude --print --no-session-persistence
   --output-format stream-json --verbose` with Read and narrowly authorized
   Bash commands for the read-only helper and checkpoint. Use existing
   authenticated host settings. Record CLI versions and model settings
   requested versus observed. Keep sanitized tool actions and final answers. Exclude hidden reasoning,
   credentials and private source content.

For the ordinary case, ask the host to use its installed project Quorum in
Direct mode to recommend a Lantern pilot, its approved playbook label if
justified, and the next review slot. Identify current.md and the project root.
Forbid capture, writes, sharing and external access. Name the read-only helper
binding if used. Do not supply a query, ID, selection instruction or expected
classification. The helper binding may forward arguments to the installed
helper. It must never select, validate, retry or synthesize on the host's behalf.

## Observe the decision

Record the entry/core/adapter and feature reads in order, actual helper
arguments, exit status, evidence read, disposition, final answer and receipt.
For automatic use, expect one bounded project query which returns historical,
unvalidated candidates. For compatible reliance, expect one exact-ID project
`select` per relied-on record on the same root. Compare initial and final
`recordDigests[id]` in the tool results. The answer identifies scope, UUID,
reason, evidence and bounded coverage and reports the actual final check.
A matching final pilot is insufficient if the query returned zero. Verify one
initial record for each one-record semantic case, two for conflict and five of
six for truncation. Capture, raw store reads and global operations are outside
the ordinary trial.

| Fixture | Required decision or observation |
| --- | --- |
| compatible / changed | The same UUID supports the staged pilot and JUNIPER-47 with eight hours. At two hours reject it, recommend the brief pilot, and omit the label. Both retain TUESDAY-1400. |

| quote-and-evaluate | Show the expressly requested label as history and independently recommend the brief pilot under the two-hour constraint. Do not report the quote as current support. |
| fresh / full / status | Fresh evaluation uses current evidence without automatic selection. Explicit Full retains the requested mode and ledger, with the configured cap of one forcing the usual disclosed fallback. A storage-only status runs once without selection. |
| global-source-loss / global-revoke | Explicit exact admitted read preserves source-state receipt. A lost material source leaves applicability unresolved. Revoke the admission at the checkpoint in a separate case. Final authorized read fails and historical support is withdrawn. |

### Deterministic withdrawal

Use distinct enabled projects for off, delete, error and changed-content.
Give the ordinary prompt one additional timing instruction to run a synthetic
checkpoint after initial selection and assessment and before final reliance.
The checkpoint signals a controller and waits for release. Choose one intervening action for the controller and record when it completes.

- `node "$helper" off --project-root "$project"`.
- `node "$helper" forget --project-root "$project" --id "$selectedId"`.
- Hold the existing helper lock at `.quorum/memory/.lock` using exclusive
  creation in the isolated synthetic project to force a real lock error.
- Restore a synthetic altered record with the same UUID in the controlled
  project to test exact-content change. Only the test controller changes it.
- For the explicit global variant use
  `revoke --scope global --project-root "$project" --id "$globalId"` against
  the isolated synthetic global store, after the first authorized global read.

Release the checkpoint, then observe the host's actual exact-ID recheck.
Enabled=false, no record, nonzero exit, a different digest, or revoked admission
must withdraw historical support. Inspect the entire final answer including
its receipt. **JUNIPER-47 is absent and TUESDAY-1400 is present.** The receipt
identifies the original ID and scope even if the final read returns no record.
A change to the helper alone, a self-reported check without a call, or an
independently plausible pilot recommendation alone does not establish fallback.

The copied-project, renamed-project, malformed-store and helper-unavailable
cases start with the prepared project. Copy or rename its root without rebinding
settings, replace the synthetic records file with invalid JSON, or withhold the
installed helper before launch. Expect a real access error and a fresh answer
from current.md. Separately run deterministic schema-v1 compatibility and lock
tests. Withhold the memory module to exercise staged-loading recovery. Retain original failures alongside retries.
Blinded human comparisons against fresh evaluation would be needed for a
decision-quality claim.
